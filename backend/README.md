# Север · Rust и PostgreSQL

Сервер на Axum и Tokio обслуживает вход, регистрацию, каталог тенанта и экран «Документы». PostgreSQL хранит аккаунты, сессии, пространства и назначения. React и TypeScript отвечают за экраны, а Vite собирает их в браузерный модуль, который встраивается в бинарник. Axum проверяет доступ, готовит данные страницы и обрабатывает нативные формы. Маршруты и формы совместимы с KB-SPC-02. Серверный HTML доступен сразу, в том числе при выключенном JavaScript.

## Docker-стенд

Для просмотра проверенных срезов запустите Docker с Compose и выполните из корня проекта.

```sh
mkdir -p -m 700 app/.local
if [ ! -f app/.local/docker-dev.env ]; then
  (umask 077; printf 'SEVER_DEV_DB_PASSWORD=%s\n' "$(openssl rand -hex 24)" > app/.local/docker-dev.env)
fi
docker compose --env-file app/.local/docker-dev.env up --build -d --wait
```

По адресу [localhost:4125](http://localhost:4125/workspace) открывается сборка из текущих исходников. Compose хранит данные в отдельном томе `sever-dev_postgres-data` и применяет миграции при старте приложения. PostgreSQL доступен приложению во внутренней сети Docker. Адрес `localhost` хранит браузерную сессию стенда отдельно от рабочего `127.0.0.1:4121`. При повторном запуске Docker Desktop контейнеры возобновляют работу, если их не остановили явно. Повторите команду `up --build` для выкладки следующего проверенного среза.

Свежая база требует учётной записи и настроек тенанта. Используйте тот же `--env-file app/.local/docker-dev.env` при вызове `docker compose exec -T app sever create-account EMAIL NAME` и передайте пароль через stdin. Команда `docker compose exec -T app sever configure-tenants /dev/stdin` принимает [файл членств](../app/README.md) через stdin. В существующей копии базы используйте прежний аккаунт.

Сохраняйте локальный файл `docker-dev.env` вместе с томом. PostgreSQL задаёт пароль при первом создании базы. Генератор выше создаёт шестнадцатеричное значение, которое можно подставить в строку подключения без дополнительного кодирования.

## Встроенный плеер TeamStream

В Docker-стенде приложение открывается как `http://localhost:4125`, а оболочка плеера слушает `http://127.0.0.1:4124`. Разные имена хостов разделяют сессионные cookies. Плеер подключается только после нажатия «Открыть плеер».

Оболочка запускается командой `sever serve-teamstream` отдельным процессом без подключения к PostgreSQL. Задайте `SEVER_TEAMSTREAM_ORIGIN` приложению и оболочке, а `SEVER_TEAMSTREAM_PARENT_ORIGIN` — оболочке. Для внешнего HTTPS-развёртывания потребуется поддержка внешнего origin в приложении и прокси, который сохраняет настроенный Host оболочки. Выделите для неё отдельный сайт без общих cookies. Если оболочка не настроена, блок даёт ссылку на TeamStream.

Публичная ссылка «Севера» показывает опубликованный адрес плеера. Просмотр без входа зависит от настроек доступа к самому видео в TeamStream.

## Локальная модель для AI-подхода

Укажите в среде приложения `SEVER_LOCAL_MODEL_ORIGIN` с адресом локального HTTP-сервера модели и `SEVER_LOCAL_MODEL_NAME` с её именем. Приложение вызывает `POST /v1/chat/completions`. Для локального запуска используйте `http://127.0.0.1:<порт>`, для Docker Desktop подходит `http://host.docker.internal:<порт>`. В общей сети Docker имя сервиса модели — `model`.

Владелец пространства выбирает документ, настраивает инструкцию и запускает подход из задачи. Модель получает название задачи и ограниченный фрагмент выбранной редакции. Спецификация появится в документах после принятия результата владельцем. Без настроенной модели схема и параметры подхода доступны, кнопка запуска выключена.

## Шеринг страниц

Адресная выдача доступа и комментарии работают с текущими сессиями. Публичные ссылки и приглашения гостей требуют отдельного постоянного ключа `SEVER_SHARING_SECRET`. Укажите 32 случайных байта в URL-safe Base64 без паддинга. Один способ сгенерировать ключ:

```sh
openssl rand -base64 32 | tr '+/' '-_' | tr -d '='
```

Храните значение в конфигурации развёртывания. При смене значения ранее выданные ссылки перестают работать. Для гостевых писем задайте `SEVER_SHARING_SENDMAIL` как абсолютный путь к исполняемому sendmail в среде сервера и `SEVER_SHARING_FROM` как адрес отправителя. Настройки приглашений применяются отдельно от `SEVER_SELF_REGISTRATION`. На стенде письма можно направлять в локальный приёмник.

В JSON для `sever configure-tenants` запись в массиве `tenants` поддерживает необязательные булевы поля `allowGuests` и `allowPublicLinks`. Для существующей организации пропуск поля сохраняет актуальную политику. По умолчанию обе возможности выключены. Публичные ссылки также нужно разрешить в конкретном пространстве через «Поделиться» → «Ссылка». При запрете публикации действующие публичные адреса отзываются.

## Локальный запуск

Установите Rust и Node.js 22.12 или новее. Запустите PostgreSQL и подготовьте отдельную базу `sever` и пользователя, которому разрешено создавать таблицы в этой базе. В примере используется локальный Unix-сокет PostgreSQL. Подставьте имя своего пользователя базы и путь к сокету.

```sh
export SEVER_DATABASE_URL='postgresql://sever_app@localhost/sever?host=%2Ftmp'
npm --prefix frontend ci
npm --prefix frontend run build:server
backend/target/release/sever migrate
backend/target/release/sever serve
```

Откройте [локальное приложение](http://127.0.0.1:4121/). Сервер слушает IPv4 loopback. `SEVER_PORT` позволяет запустить проверочный экземпляр на другом порту. Публикация по внешнему адресу требует настройки HTTPS и отдельной проверки политики сессий.

`build:server` проверяет типы, пересобирает интерфейс и требует готовый бандл при сборке Rust. Для проверки сервера отдельно подходит обычный запуск Cargo. При отсутствии бандла он соберёт серверный HTML с прежними скриптами. При раннем вводе до загрузки модуля браузер сохраняет уже заполненные поля.

Для новой базы создайте аккаунт. В zsh пароль можно прочитать без эха и передать через stdin.

```zsh
IFS= read -rs 'sever_password?Пароль для аккаунта: ' &&
  printf '%s' "$sever_password" | backend/target/release/sever create-account editor@example.test 'Имя редактора'
unset sever_password
```

Команды `sever configure-tenants tenants.json` и `sever configure-space-grants grants.json` принимают прежние [форматы JSON](../app/README.md). Права создания пространства задаются в членствах тенанта. Роль назначения `null` отзывает доступ. Каждый файл применяется одной транзакцией.

Самостоятельная регистрация включается через `SEVER_SELF_REGISTRATION=true`. Укажите абсолютный путь в `SEVER_REGISTRATION_SENDMAIL` и адрес отправителя в `SEVER_REGISTRATION_FROM`. Значение `false` или отсутствие флага выключает регистрацию. Ссылка живёт 30 минут, ожидающие подтверждения хранятся в памяти процесса.

## Перенос существующей установки

1. Для репетиции возьмите согласованную копию SQLite через SQLite Backup API. Проверьте целостность и держите копию в закрытом каталоге. Для рабочего переключения остановите приём изменений на старом экземпляре до создания свежей копии.
2. Создайте отдельную пустую базу PostgreSQL. Выполните `sever migrate`, затем `sever import-sqlite /путь/к/копии/sever.sqlite`. Импорт поддерживает схемы SQLite 1–3. Он открывает исходник только для чтения, переносит данные одной транзакцией, сверяет количество записей и отказывается писать в базу с данными.
3. На проверочном экземпляре проверьте вход старым паролем, действующую сессию, прежние ссылки, каталог и меню «Документов». Для активного экземпляра проверьте те же сценарии на замороженном кандидате и затем верните прежний локальный адрес.
4. Сохраните исходную SQLite и файлы предыдущего выпуска. Если требуется возврат до записи пользовательских изменений в PostgreSQL, остановите Rust и верните предыдущий экземпляр с исходной SQLite. После записи изменений сначала остановите запись и сохраните обе базы. Для возврата на SQLite потребуется перенести изменения из PostgreSQL и сверить их.

При импорте сохраняются UUID, scrypt-хеши и соли, дайджесты сессий, членства, разрешения и операции создания. Имена пространств и их ключи сравнения хранятся как байты UTF-8, включая значения SQLite с нулевым байтом. Приложение декодирует имя перед сортировкой и показом. Поведение авторизации покрывается запросами с явной областью тенанта.

```sh
npm --prefix frontend run typecheck
cargo fmt --manifest-path backend/Cargo.toml -- --check
cargo clippy --locked --manifest-path backend/Cargo.toml --all-targets -- -D warnings
```

До переключения адреса дополнительно проверьте импорт снимка и существующую сессию, создание закрытого пространства, его видимость в каталоге и меню, повтор создания, отзыв назначения и регистрацию с тестовой доставкой.
