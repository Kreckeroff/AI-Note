# Проект правил для AGENTS.md

Этот файл — предложение для обсуждения. Он не является автоматически загружаемым AGENTS.md. При утверждении перенести согласованные правила в AGENTS.md и сохранить ссылки на документы процесса.

## Вход в задачу

Прочитать [контекст продукта](docs/project-context.md) и [процесс](docs/workflow/operating-model.md). Найти карточку фичи, её документы, версию согласований и текущее поведение в репозитории. Отсутствующий контекст продукта запросить у владельца, предварительно проверив доступные проектные документы.

При декомпозиции, работе над новой возможностью или её приёмке прочитать [навык поставки микрофич](docs/workflow/skills/microfeature-delivery/SKILL.md). Одна история описывает один наблюдаемый результат. Завершение микрофичи требует проверенной рабочей версии и записанного результата приёмки. [Шаблоны](docs/workflow/microfeature-templates.md)

## Маршрутизация

- Новая или неполно описанная фича: аналитик → при необходимости архитектор → дизайнер для пользовательского интерфейса → согласование → техническая подготовка → подтверждение старта.
- Описанная фича: проверить актуальность спецификации, макетов, контрактов и согласований; показать владельцу краткую сводку; получить подтверждение старта для конкретной версии.
- Ошибка: независимое воспроизведение QA → подтверждённый отчёт → регрессионный тест и исправление назначенным разработчиком → новый QA-проход.

## Управление

Владелец согласует требования, макеты, старт реализации и релиз. Оркестратор ведёт технические переходы и исправления внутри согласованной задачи. Изменение согласованного поведения возвращает затронутые артефакты на согласование.

При передаче задачи выбрать [роль](docs/workflow/roles.md), затем подходящие существующие навыки из [каталога](docs/workflow/skill-catalog.md). Выдать исполнителю минимальный пакет по [контракту передачи](docs/workflow/artifacts.md). Для обычного исполнения наследование истории выбирать по задаче; для независимого QA использовать новый контекст без наследования истории.

## Исполнение

Границы модулей и тестирования согласовать до реализации. Разработку вести циклами «поведенческий тест падает → минимальная реализация → тест проходит». Владельцев изменяемых файлов назначать явно. Параллельную работу вести по независимым областям.

QA проверяет фиксированную версию по утверждённому контракту. Он возвращает доказательства и список ошибок; разработчик отвечает за исправления и постоянные регрессионные тесты. После исправлений независимая проверка запускается в новом контексте. Условия завершения и выхода из повторяющегося тупика определены в процессе.

## Учёт

Оркестратор обновляет карточку фичи, ссылки на артефакты, зависимости, согласования, историю QA и план. Доска отображает те же данные; изменения через неё должны сохраняться в согласованный источник данных.
